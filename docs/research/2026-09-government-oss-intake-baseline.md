# Curated software intake: freshness and notability baseline

Snapshot: 22 September 2026 UTC. This baseline applies to **new software records** proposed for GOSDIR. It refines the existing [four evidence checks](../../app/methodology/page.tsx) and [product-plan trust rules](../product-plan.md). It does not retroactively delete quiet projects: the product plan requires stale and archived records to be labeled. The earlier [collection survey](2026-09-government-oss-collections.md) proposed 36 identities; this audit measured product maturity and significance. The later [individual-review ledger](ledger/README.md) supersedes its publication decisions.

The current ledger status is 30 publishable and six held, combining 10 earlier publication decisions with 26 new individual reviews; Malcolm, trec_eval and SIARD Suite joined the hold set for rights or first-licensed-year questions. ## Baseline for each new record

1. **Core evidence is mandatory.** Confirm material government authorship, commissioning, funding or stewardship; a reachable canonical software source; an actual OSI-approved code grant or clear public-domain grant; and primary evidence. Deduplicate by **product identity**, not only repository URL. Code inventories, mirrors, forks, documentation, example apps and multiple microservices of one product stay in the discovery queue until their independent identity is shown.
2. **Show maturity.** Require either a production government deployment, or a usable release/distribution with user documentation. A new repository less than 90 days old is held unless the product was already operating elsewhere or an official release proves maturity. Repository creation date is not product age: moved or newly opened source can be old software. Keep first public release, latest code commit, latest software release and current official-service evidence as separate dates.
3. **Measure freshness using source activity and current use.** A substantive default-branch commit or software release within **24 months** is the normal intake path. A quieter repository can pass as **Maintained** if a current official product page, distribution, support statement or deployed service establishes continuing use **and the public source still corresponds to that product**. If the last source change exceeds **48 months** and no current-use evidence exists, only an unusually significant historical project merits a clearly labeled **Archived** record; otherwise defer. An archive flag triggers review. Never infer code activity from `code.json` metadata update dates or GitLab project-event dates.
4. **Require notability evidence, not a popularity number.** At least one documented pathway must hold: (a) a named government service or officially distributed operational tool with user documentation; (b) actual reuse by an independent organization, documented scholarly/scientific use, or implementation of a government standard; or (c) an agency-published reusable product with versioned release **and** installation/user guidance. A bare catalog entry, license file, README, GitHub topic or initial code push does not meet this bar. A library, SDK or scientific tool can qualify through real use or official distribution just as an app can.
5. **Use popularity only to order review.** Record stars, forks, download counts, citations and known independent adopters when available, with source and observation date. None is a universal admission threshold. Three of four qualifying [Colorado OpenCDSS](https://opencdss.state.co.us/opencdss/) products have one GitHub star, while StateMod's code is quiet but the official product remains in use. A `≥25 stars` or `≥5 forks` flag can move an unreviewed candidate up the queue; it cannot make the candidate eligible.

For public project status, use **Active** — Ongoing development and improvement; **Maintained** — Stable; fixes and updates as needed; and **Archived** — No longer maintained; retained for reference. Review Active/Maintained records at least annually and Archived records at least every 24 months; reopen review sooner on archive, transfer, license, source URL, deployment or successor changes. A quiet commit feed triggers investigation, never automatic deletion. The [OpenSSF Scorecard maintenance check](https://github.com/ossf/scorecard/blob/main/docs/checks.md#maintained) likewise says low commit activity can be normal for small stable software.

## Effect on the existing directory

The current 32 software records include 27 labeled `Active`, three `Maintained`, and two `Archived`. Those labels and recent `verified` dates are editorial assertions, not a fresh code-activity audit. Apply the annual/24-month review cycle above instead of deleting existing records by a new numeric cutoff. Two entries, cloud.gov and Code.mil, currently use GitHub **organization** URLs in the `repository` field; identify a product-level canonical source or explicitly record why a multi-repository product needs an organization URL at their next review.

**Sizing conclusion:** the prior survey's thousands are discovery leads. The current evidence establishes **33 screen-passing named projects** from the hand-reviewed set, with no defensible estimate yet of how many thousands of metadata rows will pass product-level notability and current-source verification. Apply the same baseline to small, source-specific samples before forecasting throughput or promising a bulk import.
