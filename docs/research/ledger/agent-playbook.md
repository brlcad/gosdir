# Candidate-review agent playbook

This is the repeatable process for the [government OSS ledger](README.md). The 2026-09-28 run uses **Luna subagents at max reasoning effort** for repository-level research. A source snapshot or metadata screen is not an individual review.

## Coordinator loop

1. Refresh or add source snapshots, preserving the original record URL, repository URL, source license claim, source owner claim, retrieval time, and an explicit `candidate` or `excluded` metadata screen. Record inaccessible, no-repository, and pagination gaps in each source manifest.
2. Run `node scripts/build-government-oss-ledger.mjs` and inspect `summary.json` for source coverage, disjoint batch assignments, and review counts. A failed build means the source/review data is not accepted.
3. Allocate a unique batch with `node scripts/plan-government-oss-review.mjs --batch-id <id> --source <source-id> --limit 20`. The default `--metadata-screen candidate` prioritizes source-screened leads. Use `--metadata-screen excluded` for the remaining source entries or `all` for a mixed queue: metadata exclusion is not a four-check review. The optional `--source-metadata-flag <flag>` restricts the batch to source rows with a true priority flag, for example Swiss `stable_or_beta_standalone`; this flag orders research but does not establish eligibility. Use `--url <normalized-repository-url> --metadata-screen all` to assign one related or metadata-excluded repository for targeted product-family follow-up. Existing batches are immutable assignments; agents must not claim another batch's URLs. The planner holds an exclusive assignment lock while reading existing batches and writes each new batch atomically; if the lock remains busy after a terminated process, investigate it before changing or removing the lock. The `prior-shortlist-01` batch predates import of some publication reviews; agents must skip URLs already reviewed.
   For this full-audit run, candidate-first is only a scheduling priority. The captured universe is 78,088 distinct repository URLs (19,994 priority leads plus 58,094 metadata-excluded-only leads at the 28 September snapshot). Once priority leads are exhausted, keep planning excluded-only batches until every captured URL has an individual decision; do not treat a metadata screen as a review or stop at the priority subset.
4. Give each available Luna/max agent one bounded batch and this playbook. Keep work in separate `reviews/<batch-id>.jsonl` files. Assign more batches only after the prior tranche is validated and rebuilt.
5. Review the evidence and product-family decisions independently. Only `publishable` rows with all four checks passing, defensible attribution/year, and notability evidence are eligible for catalog drafting. Catalog edits require the ordinary project validation and editorial review.

## Per-repository review

For **every assigned URL**, follow redirects and inspect the current canonical repository. Check the first-party government page, verified organization, publiccode file, procurement/release record, or other primary source that establishes the _specific relationship_ (creation, commissioning, funding, sponsorship, or stewardship). A catalog's recommendation, government use of third-party software, topic tag, or account name alone is not enough. Inspect the actual code license text and its scope; a detected SPDX label or `code.json` field is only a lead. Compare the **exact version and variant** with the [OSI-approved list](https://opensource.org/licenses): approval of CeCILL-2.1 does not approve CeCILL-B, and approval of NIST-Software does not automatically approve a different NIST data/work notice. A U.S.-only federal public-domain statement plus a separate custom permission grant is not itself a worldwide public-domain dedication or an OSI-approved license, even if the grant is broad; hold unless another exact eligible grant or authoritative worldwide dedication exists. Check that code is public without credentials.

Decide product identity before admission: a fork, mirror, demo, data-only repository, documentation site, deployment instance, SDK, or microservice may not be an independent notable product. Apply the [freshness and notability baseline](../2026-09-government-oss-intake-baseline.md): a production government service or officially distributed operational tool with user documentation; documented independent reuse, scholarly/scientific use, or government-standard implementation; or an agency-published reusable product with a **versioned release and** installation/user guidance. A live repository or setup README alone is insufficient. Stars only prioritize review.

Open the cited page and verify its actual title/body refer to the **exact** project before recording a use, deployment, or scholarly citation. Search-result snippets, adjacent papers, model-method predecessors, or a data release in the same program do not establish use of this repository's code. For a quiet source, record a current and product-specific support/distribution/use signal; a historical DOI page remaining online does not by itself satisfy the maintained exception. When a citation is wrong or inaccessible, correct it or hold the row even if a catalogue field looks promising.

For a multi-repository service, distinguish an umbrella/work-tracking repository from the deployed application code. Its license does not automatically cover linked frontend, backend, or harvester repositories. Verify the material components' source grants before assigning a product-wide license or mark the product `hold` with the unresolved scope.

For a publishable row, research the **first defensible year public licensed source was available**. Repository creation, catalog release date, and code-inventory `lastModified` are not interchangeable. Use dated releases, archived public pages, commit/license history, or primary release records. If the year or material sponsor remains uncertain, mark `hold` with the gap; do not guess. Capture a specific agency and geography, not only a country or platform account when a more precise sponsor is known.

Each review JSONL row must include the **assigned normalized source URL**, UTC review time, reviewer, `decision` (`publishable`, `hold`, `reject`), factual reason, and all four `checks`: `government_provenance`, `public_source`, `eligible_license`, `primary_evidence`. Each check has `result` (`pass`, `fail`, `unresolved`), direct `evidence_url` when available, and a short note. Include `product_identity`, `agency`, `geography`, `open_source_year`, `license`, `official_url`, `notability_evidence_url`, and useful status/family notes. A rejection needs the decisive failing fact; a hold names the missing evidence or ambiguity. Model/effort provenance is tracked by the coordinator from agent assignment, not guessed by the reviewer.

When extending a review file, merge by normalized repository URL and check for an existing row before writing. Do not append a second copy of any decision; if duplicate rows appear, inspect whether their evidence or decisions differ before removing only exact duplicates. Rebuild after each tranche so an invalid batch cannot silently accumulate.

When the source URL is a branch, migration notice, mirror, download, or search result rather than the canonical code root, keep the assigned URL as the reviewed lead and record the separate `canonical_repository_url` only after proving the link. Do not transfer a license or sponsor claim from an old URL to a successor without inspecting the successor.

## Acceptance gate

- The review URL exists in a source snapshot and appears in exactly one review file.
- Four checks are separately documented; no `publishable` decision has a failed/unresolved check.
- Direct URLs support the claims made in notes, including the government-to-project relationship, code license scope, and notability pathway.
- Redirects and product-family duplicates are identified; an existing catalog match is not counted as a new addition.
- `node scripts/build-government-oss-ledger.mjs` succeeds and its `batch_progress` moves from unreviewed to a real decision. The coordinator spot-checks the sources before any catalog publication.

The current repository counts and unassigned queue are generated in [summary.json](summary.json). Do not report inventory or batch assignment counts as completed individual reviews.

Full-audit completion has two independent gates: (1) every distinct URL in the captured source inventory has an individual review decision, including metadata-excluded-only URLs, and (2) every named source-enumeration gap in [coverage.md](coverage.md) has been resolved and its newly found entries reviewed. If access limitations leave a gap unresolved, keep it explicit and report the audit as incomplete rather than substituting a sampled review or an inventory count.
